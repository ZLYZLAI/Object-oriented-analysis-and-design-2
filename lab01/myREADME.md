# Отчёт по лабораторной работе
## Порождающие паттерны проектирования

**Тема:** Реализация паттерна «Строитель» (Builder) на языке C# для системы конфигурации ПК

---

## 1. Цель работы

- Изучить теоретические основы порождающих паттернов проектирования, в частности паттерна «Строитель».
- Научиться разделять логику конструирования сложного объекта от его представления.
- Реализовать гибкую систему сборки персональных компьютеров с различными характеристиками.
- Закрепить навыки проектирования расширяемых систем на языке C# с использованием графического интерфейса Windows Forms.
- Провести сравнительный анализ монолитной архитектуры и архитектуры, основанной на паттернах проектирования.

---

## 2. Описание предметной области

В рамках данной работы рассматривается задача разработки ПО для автоматизированного подбора комплектующих персонального компьютера. Предметная область характеризуется следующими факторами:

| Фактор | Описание |
|---|---|
| **Сложность объекта** | Компьютер состоит из множества взаимозависимых компонентов (процессор, видеокарта, материнская плата, ОЗУ, накопитель, система охлаждения) |
| **Вариативность** | Существуют различные сценарии использования (Игры, Офисная работа, Учёба), каждый из которых требует специфического набора деталей |
| **Бюджетирование** | Внутри каждой категории существует разделение на ценовые сегменты: Дешёвый, Средний, Дорогой |
| **Расширяемость** | При появлении новых категорий ПК система не должна требовать полной переработки существующего кода |

---

## 3. Решение: применение паттерна «Строитель»

Для решения поставленной задачи был выбран паттерн **Builder (Строитель)**. Он позволяет создавать сложные объекты пошагово, используя один и тот же процесс конструирования для различных представлений объекта.

В проекте паттерн используется следующим образом:

- **Разделение на этапы** - процесс сборки разбит на отдельные методы (`SetCPU`, `SetGPU` и т.д.), что позволяет контролировать каждый шаг.
- **Изоляция логики** - UI-форма (клиент) не знает, какой именно процессор подходит для игрового ПК - она лишь инициирует процесс через интерфейс.
- **Делегирование** - за порядок сборки отвечает специальный класс **Директор**, который гарантирует соблюдение технологического цикла создания продукта.

### 4.2. Детальное описание классов

#### Класс `Computer` (Продукт)

Конечный объект. Не содержит логики выбора - только свойства для хранения названий деталей и итоговой цены.

```csharp
public class Computer
{
    public string CPU { get; set; }
    public string GPU { get; set; }
    public string Motherboard { get; set; }
    public string RAM { get; set; }
    public string Storage { get; set; }
    public string Cooling { get; set; }
    public int TotalPrice { get; set; }

    // Метод формирования итогового отчёта
    public string GetDescription()
    {
        return $"Процессор: {CPU}\nВидеокарта: {GPU}... ИТОГО: {TotalPrice} руб.";
    }
}
```

#### Интерфейс `IPCBuilder`

Определяет абстрактные шаги конструирования. Любой новый тип сборки обязан реализовать эти методы.

```csharp
public interface IPCBuilder
{
    void SetCPU(string budget);
    void SetGPU(string budget);
    void SetMotherboard(string budget);
    void SetRAM(string budget);
    void SetStorage(string budget);
    void SetCooling(string budget);
    void CalculatePrice(string budget);
    Computer GetResult(); // Метод возврата готового объекта
}
```

#### Класс `GamingBuilder` (Конкретный строитель)

Реализует логику подбора комплектующих для игрового сегмента. Аналогично реализованы `OfficeBuilder` и `StudyBuilder`.

```csharp
public class GamingBuilder : IPCBuilder
{
    private Computer _pc = new Computer();

    public void SetCPU(string budget)
    {
        if (budget == "Expensive")     _pc.CPU = "Intel Core i9-14900K BOX";
        else if (budget == "Medium")   _pc.CPU = "Intel Core i5-13400F OEM";
        else                           _pc.CPU = "Intel Core i3-12100F OEM";
    }

    // ... реализация остальных методов: SetGPU, SetRAM и т.д.

    public Computer GetResult() => _pc;
}
```

#### Класс `Director` (Директор)

Управляет процессом сборки. Задача - вызвать методы строителя в правильном порядке.

```csharp
public class Director
{
    public void ConstructPC(IPCBuilder builder, string budget)
    {
        builder.SetCPU(budget);
        builder.SetGPU(budget);
        builder.SetMotherboard(budget);
        builder.SetRAM(budget);
        builder.SetStorage(budget);
        builder.SetCooling(budget);
        builder.CalculatePrice(budget);
    }
}
```

## 5. Вывод и сравнительный анализ

### 5.1. Сравнение подходов

| Характеристика | Без паттерна  | С паттерном Builder |
|---|---|---|
| **Связность кода** | Сильная: UI напрямую зависит от цен и названий деталей | Слабая: UI работает с абстракцией `IPCBuilder` |
| **Дублирование** | Логика повторяется в каждом блоке `if-else` | Логика вынесена в специализированные классы-строители |
| **Расширение** | Требуется изменять основной метод `FinishAssembly` (риск сломать всё) | Достаточно создать новый класс-строитель, не трогая старый код |
| **Читаемость** | Метод на 200+ строк становится нечитаемым | Код разбит на мелкие, логически понятные методы |
| **Тестирование** | Невозможно протестировать подбор деталей отдельно от формы | Можно писать Unit-тесты для каждого строителя отдельно |

### 5.2. Влияние паттерна на архитектуру

Внедрение паттерна «Строитель» коренным образом изменило архитектуру приложения:

- **Принцип единственной ответственности (SRP)** - форма отвечает только за отображение, Директор - за алгоритм сборки, Строители - за конкретные спецификации.
- **Устойчивость к ошибкам** - при правках «Офисной сборки» физически невозможно случайно изменить «Игровую сборку», так как они находятся в разных классах.
- **Гибкость** - изменив порядок шагов в одном месте (класс `Director`), изменение применится ко всем типам компьютеров сразу.

> **Итог:** использование паттерна превратило плохо читаемый код в полноценную, масштабируемую систему, готовую к эксплуатации и поддержке.
